# 生産者特化の設計メモ（坂田さん目線）

作成日：2026年10月11日

`docs/01_spec.md`（チームの仕様書）は変更せず、生産者特化で考えた内容をこのファイルに書き足す。
各項目には、01_spec.md のどこへの付け足しかを書く。

前提：三上さんと坂田さん、2人の課題を解決する。そのうえで、坂田さんが少ない手間で出品し、申し込みを迷わず選べるようにする（`docs/02_role_message.md`）。

## 1. 少ない手間で出品する（01_spec.md 4章 B-② への付け足し）

**問い：** 畑仕事の合間の数分で出品を終えるには、何を省けるか？（何回のタップで終わるか数えてみる）

### 手間がかかりそうな項目

01_spec.md の出品項目（10個）のうち、次の2つが特に手間だと考えた。

- **単価**：相場・送料・選別・梱包を考える必要がある。規格外品や余剰品は、通常品と別の値段を考える必要がある。
- **最低注文量・注文単位**：飲食店が扱いやすい量と、坂田さんが出荷しやすい量は違う。小さい飲食店は、量が多すぎると困る。

### 単価（再検討中）

- 最初は「AIが相場などを考慮した価格を提案し、最終判断は坂田さんが行う」案を考えた。
- AIが何を根拠に提案するか（AIは今週の相場を知らない、AIに渡せる情報は限られる）を考えた結果、いったん保留にして考え直す。
- 結論：単価は省略せず、AIの提案も使わない。01_spec.md のとおり、坂田さんが自分で入力する。

### 最低注文量・注文単位：「探しています」を参考にする

決めたこと：

- 最低注文量の入力欄の下に「『探しています』を確認してみる」を表示する。
- 押すと、飲食店の「探しています」の一覧を表示する。一覧は、希望数量が少ない飲食店から順に並べる。
- 一覧は、最初から次の2つで絞り込んだ状態で表示する（坂田さんが絞り込みの操作をしなくてよい）。
  - 生産者プロフィールの「畑の地域」に近い地域の「探しています」
  - 出品画面で入力済みの「食材名」と同じ食材の「探しています」

そう決めた理由：

- 「探しています」は、坂田さんがまだ出品していなくても見られる。購入希望は出品後にしか届かないので、最初の1回目の手がかりになるのは「探しています」のほう。
- お店が求める量に合わせた出品ができ、三上さんの廃棄（量が多すぎる）を減らすことにもつながる。
- すでに入力済みの情報で絞り込むので、地域を選ぶ操作（約3タップ）が不要になる。

使う情報：

- 「探しています」は、地域と条件だけを生産者に公開する。店名・住所は見せない（01_spec.md 4章 A-④、補足）。
- 検索しただけで公開していない仕入れ条件は使わない（不変条件4：他人の情報は見えない）。

希望数量が少ない順に並べる理由：

- 少ない量に合わせて最低注文量を決めると、より多くの飲食店（小さいお店も）に野菜を届けられる。坂田さんにとっては、繋がれる店が増える。

### 最低注文量：出荷の負担を件数で見せる

少ない順に並べると、坂田さんが一番上の小さい量につられて、出荷が大変な量まで最低注文量を下げてしまうおそれがある。小分け・梱包・発送は1件ごとに発生するので、負担は「少量の注文の件数」で決まる。そこで、次のようにする。

- 最低注文量を入力したとき、その場で「最大◯件の発送になる可能性があります」と表示する。
  - 最大件数 ＝ 販売可能総量 ÷ 最低注文量（アプリが計算する。AI は使わない）
  - 例：賀茂茄子30kg、最低注文量1kg → 最大30件。3kg → 最大10件。
- 坂田さんは、あらかじめ「1回の出荷で何件までなら対応できるか」（例：10件）を設定しておく。
- 最大件数がその基準を超えたら「負担が大きい」と表示する（例：大・中・小の表示や、数字を赤くする）。

| 最低注文量 | 最大件数 | 坂田さんの基準 | 判定 |
|---|---|---|---|
| 1kg | 30件 | 10件 | 負担が大きい |
| 2kg | 15件 | 10件 | 負担が大きい |
| 3kg | 10件 | 10件 | 大丈夫 |
| 5kg | 6件 | 10件 | 大丈夫 |

考え直した点：

- 最初は境目を「最大件数の〇割」にする案を考えた。しかし、ある数とその数の一部を比べると必ず「大」になるため、境目は表示する数字とは別の、坂田さん自身の基準（対応できる件数）にした。

「1回の出荷で何件まで」の設定：

- 基本は、生産者プロフィールの作成時に1回設定する（出品のたびに入力しなくてよい）。
- いつでも変更できるようにする。忙しい時期など、状況が変わったときに反映できる。
- 出品画面の最大件数の表示のそばに、今の基準と「件数を変更する」を表示する。坂田さんは、プロフィール画面に移動しなくても、出品しているその場で基準を思い出し、直せる。

```
最低注文量  [ 1 ] kg

  最大30件の発送になる可能性があります
  あなたの基準：1回の出荷で10件まで → 負担：大

  [件数を変更する]
```

「負担が大きい」ときの扱い：

- 注文の受付は止めない。受け付けるかどうかは坂田さんが判断する（「今週は多めに出す」という選択もできるようにするため）。
- 「負担が大きい」のまま「出品する」を押したときだけ、そのまま出品せず、一度注意書きを表示する。基準の範囲内なら、注意書きは出さずにそのまま出品する。
- 出品後も、届いた注文は注文ごとに承認・見送りできる（01_spec.md 4章 B-⑤）。

```
（最低注文量 1kg、最大30件、基準10件 → 負担：大 のまま）

[出品する] を押す
   ↓
┌───────────────────────────────┐
│ 最大30件の発送になる可能性があります。│
│ あなたの基準（10件）を超えています。  │
│ このまま出品しますか？               │
│                                     │
│  [最低注文量を見直す] [このまま出品する]│
└───────────────────────────────┘
```

出品画面で「件数を変更する」を押したとき：

- プロフィールの基準まで変える（次の出品にも使われる）。忙しい時期は出品が続くことが多く、出品ごとに変えるのは大変なため。
- 忙しい時期のあとに基準を戻し忘れると、本当は対応できる件数でも「負担：大」と注意書きが出て、必要以上に最低注文量を上げてしまい、小さいお店が申し込めなくなるおそれがある。
- ただし、出品画面には出品のたびに今の基準が表示されるので、坂田さんは戻し忘れに気づいて、その場で直せる。

「探しています」の一覧の見せ方：

- 出品画面の上に、画面の下から一覧が重なって出てくる形（ボトムシート）で表示する。
- 理由：
  - 別の画面に移動しないので、入力済みの食材名・総量・単価などが消えない。入力し直す手間がない。
  - 閉じればすぐ最低注文量の欄に戻れる。
  - 出品画面の中に一覧を広げる形（折りたたみ）と比べて、出品画面が縦に長くならず、スクロールの手間が増えない。
- 困る点（一覧が長いと見づらい）は、「畑の地域」と「食材名」で絞り込むことで小さくできる（仮説：実際の件数は使ってみて確かめる）。

「探しています」が0件のとき：

- ボトムシートの最初に、0件であることを一言書く（例：「今、この地域で賀茂茄子を探しているお店はありません」）。何も書かずに真っ白だと、坂田さんが不安になるため。
- そのうえで、出荷の負担（最大件数の表示）を目安に最低注文量を決めるよう案内する（例：「出荷の負担を目安に決めてみましょう」）。「探しています」がなくても、最大件数の表示は出品画面に残っているので、それを判断材料にできる。
- 絞り込みを広げて遠い地域の「探しています」を見せる案は採らない。遠いお店に合わせると、配送の負担がさらに大きくなる可能性があるため。

「代替野菜も可」の「探しています」の扱い：

- 坂田さんの一覧に出す。例：三上さんが「万願寺唐辛子 2kg、代替野菜も可」で公開していれば、伏見甘長を出品しようとしている坂田さんの一覧に出てくる。
- 理由：
  - 三上さん：代替野菜でも希望量で仕入れられ、市場での仕入れの時間を減らせる。
  - 坂田さん：余剰品を減らせる。自分の野菜を知ってもらえる。ほかの野菜も今後買ってもらえるきっかけになる（仮説）。
- 何が何の代わりになるかは、**三上さん（買う側）が決める**（01_spec.md 4章 A-③・④ への付け足し）。
  - 「探しています」を公開するとき、AI が代替野菜を提案し、三上さんが「これならOK」と選んだものだけを保存する。AI は提案だけで、決めない（不変条件5）。
  - 坂田さんの一覧は、出品する食材名が「探しています」の食材名、または三上さんが選んだ代替野菜に含まれるかで、アプリが絞り込む。
  - 理由：勝手に選ばれた代替野菜が届いて使えなかった場合、三上さんの廃棄（もったいない）が増えてしまうため。
  - 坂田さんの入力は増えない。

「種類を問わない」の「探しています」の扱い：

- 近くの地域（畑の地域での絞り込みに入るもの）の「種類を問わない」は、どの野菜を出品するときも一覧に出す。遠い地域のものは、配送の負担が大きいため出さない（畑の地域での絞り込みで、もともと外れる）。

一覧の分け方（タブ）：

- ボトムシートの上に、3つのタブ（見出しを押すと中身が切り替わる仕組み）を並べる。
  - 「（出品する食材名）」：その食材を指定したお店
  - 「代替野菜OK」：三上さんが代替野菜として選んだものに、出品する食材が含まれるお店
  - 「種類を問わない」
- それぞれのタブの中で、希望数量が少ない順に並べる。
- 理由：坂田さんが一番知りたいのは「出品する食材を欲しいお店が、どのくらいの量を欲しがっているか」。3種類が混ざると見分けにくく、「少ない順」の並べ方も崩れるため。

```
┌──────────────────────────────┐
│ [賀茂茄子] [代替野菜OK] [種類を問わない] │
├──────────────────────────────┤
│ お店A　1kg                      │
│ お店C　2kg                      │
│ ……                             │
└──────────────────────────────┘
```

最初に表示するタブ：

- 最初は出品する食材名のタブ（例：賀茂茄子）を表示する。
- そこが0件なら「代替野菜OK」、それも0件なら「種類を問わない」を自動で表示する。坂田さんがタブを押して探す手間を省くため。
- 「代替野菜OK」を「種類を問わない」より先にする理由：お店が必要としている野菜がより明確で、量の参考として確かなため。
- 3つとも0件なら、上の「『探しています』が0件のとき」の表示を使う。

### 余剰理由 → 「品の状態」を選ぶだけにする（01_spec.md 4章 B-②、5章 1 への付け足し）

01_spec.md では「余剰理由（任意。例：規格外、豊作）」となっている。これを、次のように変える。

- 文字を入力するのではなく、選ぶだけ（タップするだけ）にする。
- 欄は2つの枠に分ける。
  - **品の状態（必須）**：「通常品」か「規格外」のどちらか1つを選ぶ。
  - **余剰品かどうか**：余剰品（豊作など）の場合だけ、次の枠で選ぶ。通常品・規格外のどちらとも組み合わせられる。
- 伝えたいことがあれば、自由に書ける欄（任意）に書く。例：「形はきれいだが少し小ぶり。皮に小さな傷がある」のように、通常品か規格外か迷う場合は、その旨を書く。

```
品の状態（必須）
[ 通常品 ] [ 規格外 ]   ← どちらか1つ

余剰品の場合は選んでください
[ 余剰品（豊作など） ]

伝えたいこと（任意）
[                              ]
```

理由：

- 選ぶだけなので、坂田さんの手間が少ない。
- 品の状態を必須にするのは、飲食店との認識の違いをなくすため。何も書いていない出品が、届いたら規格外だった場合、三上さんは不満を感じる。
- 通常品と規格外は同時に選べないようにし、「余剰品だけ」を選ぶこともできないようにする。三上さんが、ふつうの品か規格外かを必ず分かるようにするため。

## 2. 申し込みを迷わず選ぶ（01_spec.md 4章 B-③・④ への付け足し）

**問い：** 4つのお店から別々の量の申し込みが来たら、坂田さんは何を見て決めるか？

### 坂田さんが見るところ

- 坂田さんが気にするのは、最初は商品代と送料（どれだけ利益があるか）だと考えた。
  - ただし、01_spec.md では「利益」「手取り額」とは表示しない（4章 B-④）。アプリは、梱包の材料費や実際の送料を知らないため。利益は坂田さん自身が考え、アプリは商品代と送料を分けて見せる。
  - 単価はどのお店にも同じ（坂田さんが決めた値段）なので、商品代は数量に比例するだけで、お店ごとの差は小さい。
- 在庫が足りていて全部承認できる場合でも、坂田さんが迷うのは**受け渡し方法と納品日**。お店ごとに、坂田さんの作業（いつ・どうやって届けるか）が違うため。
  - 例：10/20 に宅配発送が2件重なると、その日に小分け・梱包・発送を2回行う必要がある。

### 申し込みの一覧を、納品日ごとに並べる（01_spec.md 4章 B-③・④ への付け足し）

- 申し込みの一覧を、お店ごとではなく**納品日ごと**にまとめて並べる。
- 理由：申し込みが増えても（例：20件）、どの日にどのくらい仕事があるかが分かりやすく、大変な日に気づきやすい。
- 日付の見出しに、その日の件数と、1つ目の問いで決めた「1回の出荷で何件まで」の基準を表示し、超えていればそれを表示する。出品のときの基準を使い回すので、新しく入力するものは増えない。

```
■ 10/20（宅配発送 12件）
  あなたの基準：1回の出荷で10件まで → 2件超えています

  お店A　1kg　宅配発送
  お店D　5kg　宅配発送
  ……

■ 10/21（自分で配達 1件）
  お店B　2kg　自分で配達
……
```

### 基準を超えた日があるとき：納品日をずらす提案をする

- 基準を超えた分の申し込みには、**納品日をずらす提案（条件変更）**をする。お店が再同意したら販売確定になる（01_spec.md 補足「承認は注文単位で行う。変更は店が再同意するまで確定しない」の流れを使う）。
- 理由：
  - 坂田さん：1日の作業が基準を大きく超えるのを防げる。
  - 三上さん：日付はずれるが、野菜は受け取れる。
- 検討して採らなかった案：
  - 超えた分を見送る：坂田さんは楽だが、お店が野菜を受け取れない。
  - 全部承認してがんばる：お店は全員受け取れるが、坂田さんに無理が出る。

どのお店に提案するか：

- **使用日（お店が料理に使う日）まで余裕があるお店**に提案する。1日遅れても料理に間に合うので、受け入れてもらいやすい。
  - 例：納品日 10/20・使用日 10/20 の夜のお店A より、納品日 10/20・使用日 10/23 のお店E に提案する。
- そのため、申し込みの一覧に**使用日を表示する**（01_spec.md 4章 B-③ への付け足し）。

使用日の見せ方（不変条件4：他人の情報は見えない）：

- 飲食店が購入希望を送るとき、「使用日を生産者に表示する」というチェック項目を用意する（01_spec.md 4章 A-⑤ への付け足し）。チェックを入れたときだけ表示する。
- 使用日が見えるのは、そのお店が申し込んだ相手の生産者だけ。
- チェックを入れなかったお店は、納品日をずらす提案の**候補から外すだけ**。申し込み自体は、ほかのお店と同じように扱い、不利にしない。
  - 理由：見せなかったお店ほど断られやすいと、お店は本当は見せたくなくてもチェックを入れることになり、本人が選べる意味がなくなるため。

使用日に余裕があるお店が多いときの順番（不変条件6：公平に並べる）：

- アプリが、次の順番で提案の候補を並べる。
  1. **これまでに納品日をずらされた回数が少ないお店**から（回数はアプリが記録する）
  2. 回数が同じなら、**使用日に余裕があるお店**から
  - 使用日を見せていないお店は、候補に入れない（上のとおり、申し込み自体は不利にしない）
- 実際に提案を送るのは坂田さん。アプリが自動で送るのではなく、坂田さんが確かめてから送る。間違いが起こらないように、最終判断は坂田さんが行う。
- 理由：
  - 余裕の大きさだけで決めると、早めに申し込む計画的なお店ほど毎回ずらされ、予定を狂わされる不満が生まれる。
  - 「申し込みが遅いお店から」にすると、計画的な申し込みを忘れがちなお店が毎回不利になる。
  - 「坂田さんが自由に選ぶ」にすると、個人的な考え（仲の良いお店を優先するなど）が反映されやすい。

```
提案する順番（アプリが並べる）
 1. ずらされた回数が少ないお店から
 2. 回数が同じなら、使用日に余裕があるお店から
 ※ 使用日を見せていないお店は、候補に入れない
```

お店が納品日の変更に同意しなかったとき：

- 坂田さんは、提案を送る時点で「もし断られたら、どうするか」を1つ選んでおく。
  - 元の日程で販売を確定する
  - 見送る
- 選んだ内容は、お店の画面にも表示する。お店は、断ったらどうなるかを先に知ったうえで答えられる。
- 理由：両者とも納得がいくようにできるため。
  - 申し込みを終わりにするだけだと、坂田さんは楽だが、三上さんは野菜が手に入らず、次回も使ってくれるか怪しくなる。
  - 断られたあとに元に戻して坂田さんがもう一度考えると、坂田さんの手間が増える。
  - 先に決めておけば、坂田さんは1タップ増えるだけで、あとで考え直す手間がない。
- お店が答えずに回答期限を過ぎた場合は、坂田さんの選んだ内容にかかわらず**期限切れ（未成立）**にする。飲食店側の合意がないため（01_spec.md の「販売確定」は双方の合意が条件）。

```
（坂田さんの画面）
お店E に納品日の変更を提案します
  10/20 → 10/21

もし断られたら：
  ( ) 元の日程（10/20）で販売を確定する
  ( ) 見送る

        [提案を送る]
```

```
（お店E の画面）
坂田さんから納品日の変更の提案が届きました
  10/20 → 10/21
  ※ 断った場合は、元の日程（10/20）で届きます

  [10/21 で同意する]  [断る]
```

受け渡し方法ごとの基準：

- 「1回の出荷で何件まで」の基準を、**受け渡し方法ごとに別々に**持つ（例：宅配発送10件まで、自分で配達3件まで、引き取り15件まで）。1つ目の問いで決めた基準（1つだけ）を、ここで変える。
- 理由：受け渡し方法によって、坂田さんの作業の重さが違う（宅配発送・自分で配達は、引き取りより負担が大きい：仮説）。設定の手間は増えるが、その後の出品や申し込みの判断のときの負担が軽くなる。
- 検討して採らなかった案：
  - 宅配発送と自分で配達だけ数える：簡単だが、引き取りが多い日の負担が見えない。
  - 作業の重さで重みをつける：実際の負担に近いが、重みを誰が決めるのか、坂田さんに分かりにくい。

基準の使い方：

- 申し込みの一覧（納品日ごと）：その日の件数を、受け渡し方法ごとに、それぞれの基準と比べる。
- 出品画面の「最大◯件」：出品の時点では、どのお店がどの受け渡し方法を選ぶか分からない。そこで、**その出品で対応する受け渡し方法のうち、一番少ない件数しかこなせない方法の基準**と比べる（最悪の場合でも大丈夫かを知らせるため）。
  - 例：基準が宅配発送10件・自分で配達3件・引き取り15件で、今回の出品は「宅配発送」と「引き取り」だけに対応する場合 → 宅配発送の10件と比べる。

## 3. 売れ残ったときの次の選択（01_spec.md 4章 B-⑤ への付け足し）

**問い：** 売れ残ったとき、坂田さんは次に何を選べるとよいか？

### 坂田さんが困ること

例：賀茂茄子30kgを出品し、12kgが販売確定、18kgが売れ残った。01_spec.md では、残量について「販売を継続する／条件を見直して再出品する／受付を終了する」から選ぶ（4章 B-⑤）。

- 販売を継続しても、時間がたつと野菜が傷んで使えなくなる（何日もつかは野菜による。確かめが必要）。
- 受付を終了すると、余った野菜を市場に出し、仲卸が決めた値段で売るしかなくなる（2章の課題に戻ってしまう）。
- つまり、坂田さんは「早く、でも自分の値段で売り切りたい」。

最初は「まだ申し込んでいないお店に、お試しで送る」案を考えた。しかし、無料にすると坂田さんの負担（商品代・送料・梱包）が大きく、少量ずつ送ると18kgを売り切るのに件数が増えすぎる。目的を2つに分けて、今すぐ大事な「今ある野菜を傷む前に売り切る」を先に考える。

### 売れ残りの画面に「探しています」を出す（01_spec.md 4章 B-⑤ への付け足し）

- 3つのボタンを**押す前**に、近くの「探しています」の件数と合計量を表示する。
  - 理由：欲しいお店がいることを知らないまま「受付を終了する」を押して、市場に出してしまうのを防ぐ。ボタンを選ぶ判断材料にする。
  - 件数と量の両方を出す。18kgのうち、どのくらい売れそうかを坂田さんがひと目でつかめるようにするため。
  - 1つ目の問いの3つの分け方（指定／代替野菜OK／種類を問わない）と、絞り込み（畑の地域・食材名）を使い回す。「一覧を見る」で、1つ目の問いのボトムシートを開く。

### 「探しているお店」にまとめて知らせる

- 「探しているお店に出品を知らせる」ボタンを押すと、アプリが出品の情報（食材名・量・単価・受け渡し方法など）を、該当する「探しています」のお店にまとめて届ける。
  - 坂田さんは文章を書かなくてよい（6件に1件ずつ文章を書いて送るのは、畑の合間ではできない）。
  - 店名・住所は坂田さんに見せず、アプリの中でお店に届ける（不変条件4）。
- 知らせを受け取ったお店は、出品を見て、自分で**購入希望を送る**。知らせだけで自動的に買うことにはしない（01_spec.md の対象外「自動購入」）。
  - そのあとは、今までと同じ流れ（回答待ち → 坂田さんが承認 → 販売確定）になる。新しい流れを作らないので、不変条件1（売りすぎない）・3（決めた流れ以外は起こさない）をそのまま守れる。

┌─────────────────────────────┐
│ 近くの「探しています」              │

│  代替野菜OKのお店　　　　　1件・合計 2kg │
│  種類を問わないお店　　　　2件・合計 8kg │
│  [一覧を見る]                     │

```

```

      [出品を見る]

### 受付期限が過ぎたあとに知らせる場合

- 受付期限が過ぎたままでは、知らせを見たお店が購入希望を送れない。そこで、受付期限を延ばせるようにする。
- 延ばす日数は、カレンダーではなく**日数のボタン**から選ぶ（例：[あと1日] [あと2日] [あと3日]）。
  - 理由：野菜はできるだけ早く売り切る必要があるので、短い日数だけを選べるようにして、延ばしすぎを防ぐ。タップ1回で選べる。
  - ボタンの日数（1〜3日）が合っているかは、野菜がどのくらいもつかによる（仮説：確かめが必要）。
- 回答期限は、アプリが自動で**新しい受付期限の1日後**に設定し直す。坂田さんの操作は増えない。
  - 理由：早く販売確定にして、野菜が傷む前に飲食店に届けるため。回答期限を長くしても、申し込むお店は増えない（申し込みが増えるかどうかは受付期限で決まる）。承認はタップするだけなので、1日でも坂田さんは返事ができる。
  - 検討して採らなかった案：もとの出品と同じ間隔にする（坂田さんの返事のペースは守れるが、届くのが遅くなり野菜が傷みやすい）。

- まだ坂田さんの野菜を知らないお店に知ってもらう方法（売れ残りのとき以外のタイミングで）
